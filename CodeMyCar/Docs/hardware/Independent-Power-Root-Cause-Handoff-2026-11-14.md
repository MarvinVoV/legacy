# 独立供电问题根因与交接说明（2026-11-14）

本文件写给接手独立供电 / 舵机抖动问题的后续 agent。它回答一个问题：
**为什么 2026-11-14 白天用 A1–A5 反复实验都没能收敛，而晚上换一套接地拓扑后一次通过。**

---

## 0. 一句话结论

之前所有实验都保留了 **STM32 的 USB 供电**，所以"主板地—电脑/USB 电源地—市电"这条参考地路径一直在。
当两块主板**都**由同一个外部模块 5V 供电、各自 GND 单独回到模块 GND（星点）、两板之间**不再直连 GND**、USB 全部断开后：

- 舵机抖动消失（用户实物确认，慢速扫描全程平滑）
- 后轮正反转、停车正常（左 +50.3 / 右 +49.9 mm/s，反转 −48.1 / −48.1）
- IMU、联网、心跳全部稳定
- 换第二块电源模块重复验证，结果一致

随后又把模块的输入从 **220V AC/DC adapter 换成锂电池**，TB6612 上电瞬间的编码器
共模干扰从前者的峰值 ±5417 mm/s / 54 帧，降到 ±2 mm/s / 5 帧（纯量化噪声）——
**确认干扰源是市电 adapter 的共模耦合**，详见第 5 节。

**但这套配置的"舵机不抖"只是"已验收通过"，不是"已定位到唯一根因"。** 解释边界见第 8 节。

---

## 1. 历史复盘：A1–A5 为什么没有收敛

上一轮实验矩阵（见 [Independent-Power-A-B-C-Validation-2026-11-14.md](../archive/hardware/Independent-Power-A-B-C-Validation-2026-11-14.md)）：

| 组别 | ESP32 供电 | STM32 供电 | 两板 GND | 舵机结果 |
|---|---|---|---|---|
| 已验收起点 | 电脑 USB | 电脑 USB | 直接相连 | 通过 |
| A1–A4 | 外部模块 5V | **USB** | 直接相连 / 并联短地 / 换模块地线 | **全部抖动** |
| A5 | 外部模块 5V | **USB** | 再加 TB 输出地直连 | 仍未通过 |

**共同变量：STM32 始终插着 USB。**

这带来两个后果：

1. 主板地从"模块 GND"变成了"模块 GND + USB GND"，多了一条并联路径；
2. USB 另一端如果接的是电脑或带接地的适配器，主板地就与市电地相连，形成一个大环路。

A3 试过"并联一根短地线"、A4 试过"更换模块到 ESP 的供电地线"、A5 试过"TB6612 输出地与模块地直连"——
这些都在**保留 USB 地路径**的前提下做局部修补，所以没有一次能消除环路。

> 换句话说：A1–A5 一直在问"哪根线松了"，而真正的问题是"多了一整套地路径"。

---

## 2. 根因机理

### 2.1 不是"没共地"，是"共地方式不对"

用户当时的直觉是"感觉像没共地"，但两板 GND 实际上是连通的。
问题在于**连通之后电流走哪条路**：

```
ESP32 的 WiFi 发射电流（300–400 mA、毫秒级脉冲）
    → 回流路径不再是"回到自己的电源"
    → 而是经过 STM32 的地、USB 的地、市电地，再绕回模块
```

这条路径上的任何阻抗（细杜邦线、排针、接触电阻）都会变成地线电压波动。

### 2.2 舵机为什么最先受害

舵机判断转角靠**测量 PWM 高电平持续时间**（50 Hz，500–2500 µs）。
它测的是"信号线相对自己 GND"的电压。
舵机的信号来自 STM32 PA5，GND 挂在 TB6612 地上，而 TB6612 地又连到 STM32 地——
**这条地线正好是 ESP32 脉冲电流的绕行路径**。

地一抖，舵机测到的脉宽就抖，于是来回找位置 = 用户看到的"抖得不行"。

### 2.3 为什么"不接独立电源就正常"

双 USB 时两板地是直接相连的短路径，且 ESP32 的脉冲电流在本地就被旁路电容吸收，
不会经过舵机的参考地。所以起点通过、一接独立电源就失败。

### 2.4 为什么 2026-11-14 晚上这次能通过

| 变化 | 效果 |
|---|---|
| STM32 也改由模块 5V 供电，**拔掉 USB** | 消除了 USB/市电那条地路径 |
| 两板 GND **不再直连**，各自回到模块 GND | 星形接地，只有一个参考点 |
| ESP32 只保留一条地线 | 不再构成并联回路 |
| 舵机仍由 TB6612 板载 5V 供电 | 舵机电流在电池侧闭环，不进入逻辑地 |

## 3. 已验收接线（当前基线）

### 3.1 电源

| 负载 | 来源 |
|---|---|
| ESP32 | 模块 5V |
| STM32 | 模块 5V / VIN |
| TB6612 逻辑 VCC | 模块 3.3V（或板内自供，按模块而定） |
| TB6612 VM | 12V 锂电池 **+**（粗线） |
| 舵机 VCC | **TB6612 板载 5V 输出** |
| USB | **全部不接**（仅烧录时使用） |

### 3.2 地（关键）

| 从 | 到 | 线材 |
|---|---|---|
| 电池 − | TB6612 GND | **粗线**（电机电流闭环） |
| TB6612 GND | 模块 GND（星点） | 细线，仅逻辑参考 |
| STM32 GND | 模块 GND | 单根 |
| ESP32 GND | 模块 GND | 单根（**不接 STM32**） |
| 舵机 GND | TB6612 GND | 就近 |

### 3.3 信号

| STM32 | 对端 |
|---|---|
| PA11 / PA12 | ESP32 GPIO4 / GPIO5（UART4） |
| PA5 | 舵机信号 |
| PA7 / PF6 / PF10 | TB6612 PWMA / AIN1 / AIN2（左） |
| PA6 / PF7 / PF8 | TB6612 PWMB / BIN1 / BIN2（右） |
| PA0 / PA1、PD12 / PD13 | 左 / 右编码器 |

## 5. TB6612 上电瞬间的编码器共模干扰（已定位：市电共模耦合）

### 5.1 现象

**每次给 TB6612 上电**，编码器会出现约 **1 秒**的假计数：

```
21:49:51  L=-3525  R=+3052    ← 双轮同时、方向相反
21:49:51  L=-5417  R=+3922
21:49:51  L=-5289  R=+3692
21:49:52  L=-79    R=+25      ← 约 1 秒后自行恢复
```

- 全部出现在 `mode=0 / state=idle`，**没有任何运动指令**
- **用户实物确认：轮子没有真的转**
- 双轮**同时**、**反号** → 典型共模干扰特征，不是机械运动
- 副作用：里程计被虚增（本次残留 −254 mm 偏移）、航向短时跳变

### 5.2 已排除

| 假设 | 排除依据 |
|---|---|
| 电机真的在转 | 双轮反向不可能；用户目视确认无转动 |
| 某根编码器线接触不良 | 重插左右编码器与右路信号线后**照样复现** |
| 我的命令参数导致 | 复现实验全程只发过 1 条 ESTOP，其余 90 s 无任何命令 |
| 单一通道问题 | 第一次只有右轮，重接后变成双轮，说明是共模而非单线 |

### 5.3 根因确认：市电 adapter 的共模耦合

把模块输入从 **220V AC/DC adapter** 换成 **锂电池**后，同一套 90 秒三次通断实验：

| 指标 | 220V adapter | 锂电池 |
|---|---|---|
| 90 秒内非零轮速帧 | **54 帧** | **5 帧** |
| 峰值 | **±5417 mm/s** | **±2 mm/s** |
| 单次持续 | 1–2 秒 | 单帧 |
| 里程计污染 | −254 mm | −2 mm（噪声） |

电池下的 5 帧全部是单帧的 ±1~2 mm/s 量化噪声，未形成任何持续跳变。

机理：AC/DC adapter 的输入/输出之间存在寄生电容（Y 电容），把市电的共模噪声带到
输出地；TB6612 上电浪涌激励该噪声，经电源/地耦合进入编码器 A/B 线产生假计数。
电池供电时系统完全浮地，没有市电参考，耦合路径被切断。

### 5.4 当前处置

**规避**（仍建议保留）：给 TB6612 上电后**等 3 秒**再发运动命令。

**根治方向**（如需继续使用市电供电）：

1. 换用带**隔离变压器**或共模扼流圈的低漏电流适配器；
2. 编码器 A/B 线与电机动力线分开走线；
3. 编码器 VCC/GND 取自稳定电源（STM32 3.3V），而不是随机驱动器通断的 5V；
4. 编码器输入端加 RC 滤波 / 施密特整形（需要焊接）。

## 7. 给下一位的两条操作规则

1. **TB6612 上电后等 3 秒再发第一条运动命令。**
2. **做电源通断实验时，系统必须处于 STOP 模式**（不要用 DRIVE 保持状态做通断测试——
   DRIVE 模式下电机驱动是使能的，会引入额外变量）。

## 8. 解释边界（重要）

- 本结论基于 **MQTT 遥测 + 用户实物观察**，**没有示波器、没有纹波/瞬态波形测量**；
- "市电共模耦合"是由 **A/B 对比实验**（同一拓扑，仅改变模块输入源）推得的结论，
  没有直接测量 Y 电容漏电流或共模电压；
- 新电源模块的**型号与额定电流未确认**，因此不能宣称"该模块电气质量合格"；
- 今天是**多个变量同时改变**（ESP 供电、STM 供电、地拓扑），
  不能把通过唯一归因于"星形接地"或"拔掉 USB"中的某一项；
- 每套配置只做了**分钟级**验证，不等于冷启动/带载/长期可靠性验收；
- INA219 未接入，`available=false` 不能用来证明主电源电压正常。

## 9. 复现步骤

```bash
# 1) 服务端
cd pyserver && CMCAR_VOICE_LOCAL_PLAYBACK=0 .venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

# 2) 抓包（注意：mosquitto_sub 重定向到文件时是块缓冲，需用 pty 强制行缓冲）
script -q /dev/null mosquitto_sub -h 127.0.0.1 -t 'data/#' -t 'cmd/#' -v -F '%I %t %p' >> /tmp/capture.log

# 3) 只读确认
curl -s localhost:8000/api/v1/devices

# 4) 舵机 / 电机回归
#    曲率 ±3.0 零速；正转 +50 mm/s 8 s → 停车 5 s → 反转 −50 mm/s 8 s
#    全程 10 Hz 刷新租约，异常路径 finally 发 ESTOP
```

判定标准：

- **ACK 全部 status=0** 只代表"命令被接受"，不代表实物通过；
- **必须以实物观察为准**（轮子是否转、舵机是否抖）；
- 遥测出现 `fault=true` 或 `error=8` 表示保护触发，不要反复清故障重试。
