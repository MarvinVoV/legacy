# 语音修复实施与实机验收记录（2026-11-12）

开发分支：`codex/s3-voice-architecture`。修复依据：[深入复核与计划](Voice-Architecture-Review-And-Fix-Plan-2026-11-12.md)。不合并 main，不 push，语音运动始终关闭。

## 当前结论

**核心缺陷已修复，基础功能实机验收通过；长期声学/噪声压测及后续全双工增强尚未完成。** 后续agent从本文及同目录README继续，不要将未来增强项误当成本轮已交付。

第一轮真实用户测试：唤醒正常，有较长首次等待；播报有滋滋声，在数到 18 时停止。日志证实停止来自本地 DTD 误触发，随后服务端确实取消了旧回复，静音保护后恢复监听。这轮是失败样本，不是通过样本。

修正物理参考ADC后，用户确认**完整数到20，常规TTS基本正常**；参考峰值采样约15,875、累计参考削顶0，麦克风当轮也为0。随后故事中的“停一下”实机确认**停止，旧故事未续播**。本地“我在”的开头杂音随后也完成定位与复验，见下文。

后续用户进一步确认：**讲故事→停一下→安静1–2秒→继续刚才的故事→再次停一下**，能继续相关故事，也能再次停住。这证明本轮基本上下文和取消闭环可用，但仍不代表字级精确续播。

## 已实施的代码变化

- 服务端：删除打断状态的重复清零；限制过期/重复/非 speaking 状态的打断；托管并回收 interrupt、worker、watchdog、鉴权预热及回合内预取任务。
- 协议 v2：start/ready 协商 `barge_in` 与 `playback_ack`；回复带 `turn/seq`；用 `playback_end` → `playback_finished` 和 `stop` → `stop_ack` 协调回合收尾。旧 command 客户端保留非 ACK 路径。
- 设备：取消的 turn 不能被旧 speak 重新激活；入队和出队使用 epoch 隔离；取消与 codec write 共用互斥边界，取消返回后旧生产者不能重新填队列。
- 软件播放完成包含队列、已出队数据和 **110ms DMA 保守尾窗**（当前配置 6×240/16k=90ms，另留20ms）。这是基于已知 DMA 配置的有界估计，不是声学传感器测得“喇叭绝对无声”；没有粗暴停掉共享 RX 时钟。
- 主动清空采音后重建序列边界，恢复时丢掉手中旧 PCM；播放→监听迁移先于旧帧序列校验；断线/end 统一清理输出。
- PCM 解码修复奇数字节 carry 扣账；严格限制板端支持的 PCM/16k/mono/完整样本。
- DTD：去掉跨时间窗的 raw ref/corr 与延迟 AFE RMS 混合判断。改为由 fetch owner 每个新 AFE 输出窗计算 AC RMS，结合该窗 VAD；按实际样本数确认200ms，收敛保护300ms，冷却2.5s。**此检测器仍需实机标定，不能将单测通过当作抗回声合格。**
- 移除 feed 路径昂贵的全 lag 相关搜索；增加 raw mic/ref RMS、peak、累计近满幅样本诊断。raw 与 AFE 诊断明确标记不对齐，不再伪称严格 ERLE。
- 修复 codec 接口资源泄漏和负 signed 样本左移；I2S 输出采用100ms有界写，维持已验证的32-bit stereo格式与硬件音量。
- 服务端模型→分句→TTS→下发改为有界任务流水线（两个队列各最多2项），取消时一起回收；TTS失败不记为成功播报。
- 停止词改为短命令匹配，避免吞掉“为什么要停下来”；legacy 历史按完整 user 回合裁剪；下一回合附明确的回复中断说明，不声称下发内容已全部听到。

## 实机发现与针对性修复

### 1. 参考通道严重削顶，不能继续只调 DTD 阈值

第一轮麦克风累计削顶0；参考累计约46,538个近满幅样本。示例：

```text
raw mic/ref rms=377/29208 peak=1134/32768 clips=0/7216
raw mic/ref rms=86/28052 peak=283/32768 clips=0/14328
local barge-in from fresh AFE residual/VAD windows
```

参考套用了37dB麦克风增益。已拆出独立参考增益配置，候选12dB。**逐路探测已确认物理ADC2（零基编号，MIC3/寄存器0x45）控制TDM ch1；不能将TDM ch1等同物理ADC1/MIC2。**

探测时ADC0设12dB，mic RMS降至1–2而ref约600；ADC1设12dB，ref仍约600；ADC2设12dB，ref RMS从约600降到1、peak降到4–5；ADC3设12dB，ref恢复约600。寄存器读回依次为 `14/1e/1e/1e`、`1e/14/1e/1e`、`1e/1e/14/1e`、`1e/1e/1e/14`，全部status=0。配置已改为物理ADC2，并完成正式播报复验。

新增串口 `g`：仅 idle 由采音监督任务依次把四个物理 ADC 单独设为12dB、读取0x43–0x46增益寄存器并保持1.6秒；最后恢复配置。期间暂停唤醒，持续采音，结束清空临时音频。它只用于确认物理增益作用在哪个已知 TDM slot，不调用云端、不驱动车辆。

### 2. 播放节奏与杂音分开验证

不能把参考削顶直接当成喇叭滋滋声的已证实原因。下发节奏已从相对 sleep 改为跨句共享的绝对播放时间线，最多提前200ms，避免1.25倍速持续堆积，也避免精确实时逐块 sleep 的累积漂移。停止时重置该时间线。

软件输出保留64帧上限和40ms启动等待；真实网络抖动及欠载是否改善，仍需对照用户听感与日志。

### 3. 首次网络等待

第一轮 VAD 分句完成15:41:10.663，首段TTS返回15:41:23.061，约12.4秒。两次百度鉴权合计约4.5秒，其余主要是ASR、LLM、TTS网络请求。用户确认VPN会显著拖慢百度，正常网络较快；本轮不将该延迟误判为采音故障，也不擅自更换服务。

在唤醒后后台并行预热ASR/TTS鉴权，单个预热5秒上限、失败允许正常请求重试、会话关闭时回收。每轮另外记录ASR/TTS耗时，便于分离网络与本地延迟。

### 4. 本地“我在”的开头杂音：定位与无效实验

- 用户确认从电脑播放原始PCM包装的WAV是干净的；板子重复播放仍有开头杂音，不能再归咎于录音文件。
- 按用户要求重新调用百度、使用相同音色参数生成“我在。”：与内置PCM**逐字节一致**，SHA256 `aa0a06b70359b2edb118910e0cc280b718f330fea90bb21e9e6bd4d8a856abdb`。16k/mono/PCM16、800ms、峰值19744、削顶0，DC约−0.95。
- 160ms静音预填充实机没有改善，**已从代码撤回**，不得将它当作已验证修复。
- 发现本轮改动新增的一个真实调度错误：板子 `CONFIG_FREERTOS_HZ=100`，播放等待中的 `pdMS_TO_TICKS(5)` 和满队列等待的 `pdMS_TO_TICKS(1)` 均为0；`vTaskDelay(0)`不能让出给低优先级播放任务。网络/会话任务优先级4，输出任务3，尤其本地ACK同步等排空时会忙等。已统一钳制至少1 tick，并补100Hz与1000Hz两组host测试。
- 本地ACK开始前先退出IDLE唤醒检测态，避免自己播放期间仍跑WakeNet。仍保持先本地回应、再连接网络，断网也有提示音。
- 修正调度后保持相同音频、相同音量，用户明确确认“这次干净了，没有明显杂音”。后续正常唤醒整体验收再次确认提示音干净。设备端复验通过。
