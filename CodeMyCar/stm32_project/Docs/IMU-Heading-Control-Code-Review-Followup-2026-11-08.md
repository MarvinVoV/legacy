## 1. 审查基线、范围与证据分级

审查时仓库位于 `main` 分支，STM32 部分存在一处尚未提交的改动：

- `Application/Services/Ctrl/Src/motion_service.c`

该改动包含：

1. 运动模式变化时，以当前 IMU yaw 重置航向控制器参考角；
2. 航向控制增加每秒一次的诊断日志。

本报告同时审查了已提交代码与上述未提交改动。其他工作区改动主要位于 `frontend`，不属于本报告范围。

重点阅读了：

- `Services/Ctrl/Src/{motion_service,heading_control,cmd_process}.c`；
- `System/Utils/Src/{motion_goal,motion_kinematics,steering_lut,safety_supervisor}.c`；
- `Services/{Motor,Servo,Safety}` 与 Motor HAL/driver；
- `Tasks/{MotionTask,MotorTask,CtrlTask,ServoTask,SonarTask,ImuTask}`；
- IMU SH-2 适配层、任务初始化、底盘参数及现有 host 测试。

证据分级：

- **已复现**：在电脑上直接编译调用当前产品函数，观察到具体错误输出；不代表已验证实际车辆表现。
- **代码确定**：能从状态读写和分支确定缺陷；并发问题给出可行交错，但未做真机调度复现。
- **待测风险**：代码架构存在薄弱点，实际严重程度依赖负载、机械、电源或任务调度。
- **优化建议**：改善可维护性或性能，不作为已发生故障。

GOAL 尚未接入 IMU 是功能缺口，不应与确定缺陷混为一谈；是否纳入本次修复应由功能范围决定。IMU 的 status 也不应简单要求恒为最高等级，应结合该报告类型的语义、数据新鲜度、数值有效性及实际标定状态制定准入策略。

## 2. 总体结论

当前 IMU 数据链路已打通，基础运动控制可构建，现有 host 测试通过，但完整控制链路仍存在影响停车可靠性、转向跟随和失效降级的问题，尚不能据此认定闭环控制已完成落地验收。

优先风险是 STOP 被旧运动快照覆盖、制动失败未传播、立即回中未取消旧轨迹、超声波数据无超时保护；其次是最终曲率越界回中、动态舵机目标反复清零速度、倒车反馈方向和直行误判。IMU 初始化、数据新鲜度、积分生命周期、几何边界和共享状态也需要完善。

本报告将两轮结果统一为 IMU 问题、完整控制链路问题、硬件风险和架构建议，只有一份修复优先级（第 7 节）。问题分类、验证证据和功能缺口分别标明，不能把已有构建/测试通过等同于整车控制已验证。

## 3. IMU 与航向控制问题

编号使用 `IMU-P1-xx` / `IMU-P2-xx`，对应原 IMU 审查编号；完整控制链路使用 `CTRL-xx`。

### IMU-P1-01：倒车直行时航向修正方向相反

位置：

- `Application/Services/Ctrl/Src/heading_control.c`，`HeadingControl_Apply()` 直行分支

当前直行控制使用：

```c
err = yaw - psiRef;
corr = Kp * err;
```

这一符号在前进时与当前“曲率正值表示右转”的约定匹配，但倒车时车辆运动学方向反转，继续输出相同方向的曲率会形成正反馈。

例如倒车时车头向右偏、`yaw < psiRef`：

1. 当前控制器输出负曲率；
2. 倒车状态下，该舵角会让航向继续向右变化；
3. 航向误差进一步增大。

影响：倒车直行可能越来越偏，达到修正限幅后仍持续向错误方向转向。

建议：

- 根据实际速度符号调整角度环输出方向；或
- 统一基于运动学关系 `yawRateExpected = -v * kappa` 推导反馈方向；
- 增加前进/倒车、左右扰动四组方向测试。

### IMU-P1-02：倒车转弯没有启用角速度反馈

位置：

- `Application/Services/Ctrl/Src/heading_control.c`，曲率/角速度闭环分支

当前代码仅在以下条件成立时计算实际曲率：

```c
if (vMps > 0.03f)
```

倒车速度为负，因此永远不会进入实际曲率计算。此时 `kappaMeas` 保持为 `kappaFf`，误差恒为零，闭环退化为开环。

建议：

- 低速判断使用 `fabsf(vMps)`；
- 实际曲率计算仍保留带符号速度：`kappaMeas = -yawRate / v`；
- 对零速附近设置明确死区，避免除零和噪声放大。

### IMU-P1-03：DIRECT_CONTROL 会把部分正常转弯误判为直行

位置：

- `Application/Services/Ctrl/Src/motion_service.c`，`handle_direct_control()`

当前逻辑根据左右轮 RPM 是否接近判断是否直行：

```c
straight = fabsf(leftRpm - rightRpm) <= 3.0f;
```

阿克曼小车可能在左右轮目标相同的同时，通过非零舵机曲率执行转弯。此时系统会错误启用航向保持，并逐渐抵消用户要求的转向。

建议：

- 直行判定以 `fabsf(curvature) < threshold` 为主要条件；
- 左右轮速度差只作为差速模式识别或辅助条件；
- 增加“同 RPM + 非零曲率”的回归测试。

### IMU-P1-04：IMU 停更后仍可能用旧数据控制最长 2 秒

位置：

- `Application/Tasks/ImuTask/Src/imu_task.c`
- `Application/Services/Ctrl/Src/motion_service.c`，`heading_correct()`
- `docs/IMU-Heading-Control-Design.md`，P4 异常与安全要求

当前 IMU 重连超时为 2000 ms，运动控制只检查 `yawValid`，没有检查 `lastUpdateMs` 对应的数据年龄。

因此传感器停更后：

1. `yawValid` 仍然为 true；
2. 冻结的 yaw/yawRate 继续进入闭环；
3. 最长约 2 秒后才关闭 SH-2 会话并重连。

这与设计文档要求的“连续 200 ms 无数据即关闭航向闭环、回退开环”不一致。

建议把两个阈值分开：

- 约 200 ms：数据新鲜度阈值，超过后立即退出闭环；
- 约 2 s：SH-2 会话重置/重新初始化阈值。

### IMU-P1-05：初始化失败和始终收不到首帧时无法自动恢复

位置：

- `Application/Tasks/ImuTask/Src/imu_task.c`，`ImuTask_doTask()`
- `Application/Services/IMU/Src/imu_service.c`，`ImuService_Init()`

存在两条恢复漏洞：

1. `ImuService_Init()` 失败后，`needInit` 没有重新设置为 true，不会再次尝试初始化；
2. 初始化成功但始终没有收到第一帧 GRV 时，`lastUpdateMs == 0`，当前超时条件不会触发。

此外，以下调用的返回值均被忽略：

- `sh2_setSensorCallback()`；
- `sh2_setSensorConfig(SH2_GAME_ROTATION_VECTOR, ...)`；
- `sh2_setSensorConfig(SH2_GYROSCOPE_CALIBRATED, ...)`；
- `sh2_setSensorConfig(SH2_ACCELEROMETER, ...)`。

配置失败时任务仍可能打印 `IMU ready`，然后永久停留在没有有效数据的状态。

建议：

- 初始化任何一步失败都进入带退避的重试状态；
- 单独记录初始化开始时间，覆盖“从未收到首帧”的超时；
- 只有回调注册和必要传感器配置全部成功后才设置 `inited=true`；
- 区分初始化错误、配置错误和运行期超时错误码。

### IMU-P1-06：超声波硬制动期间航向控制仍在运行和积分

位置：

- `Application/Services/Ctrl/Src/motion_service.c`
- `handle_drive()`/`handle_direct_control()` 先调用 `heading_correct()`；
- 超声波硬停止在 `MotionService_Run()` 的统一出口中稍后处理。

结果是车辆被安全制动时：

- 航向控制器仍会执行；
- PI 积分没有明确冻结；
- 舵机仍可能保持修正角；
- 障碍解除后可能带着累计积分突然恢复转向。

这与设计文档中“超声波制动时冻结积分”的要求不一致。

建议：

- 安全制动生效时显式暂停或禁用航向控制器；
- 恢复运动时用当前 yaw 重新锁定参考航向；
- 区分“暂停并保留参考”和“故障恢复后重新捕获参考”两种状态。

### IMU-P2-01：IMU 恢复后可能沿用失效前的航向基准

位置：

- `Application/Services/Ctrl/Src/heading_control.c`，`HeadingControl_Disable()`

当前禁用函数清除了积分和修正输出，但没有重置：

- `straightMode`；
- `lastTickMs`；
- `psiRefDeg`。

如果 IMU 在同一次直行命令中失效后恢复，运动模式没有变化，控制器可能继续追踪失效前的旧航向，恢复瞬间产生转向跳变。

审查时未提交的“模式变化时 Reset”改动无法覆盖这种情况。

建议在重新获得有效且新鲜的 IMU 数据时，明确执行一次“重新捕获参考航向”。

### IMU-P2-02：陀螺零偏标定按任务循环计数，而不是按新样本计数

位置：

- `Application/Services/IMU/Src/imu_service.c`，`ImuService_Update()`

当前每次 100 Hz 任务调用都会增加 `calibCount`，但没有检查 `gyroCount` 是否产生了新样本。

可能导致：

- 陀螺首帧尚未到达时，用默认零值完成标定；
- 同一个陀螺样本被重复累计；
- 任务频率变化会改变标定结果；
- 低于 5°/s 的缓慢转动被当成静止样本。

建议：

- 仅在 `gyroCount` 变化时累计一次；
- 结合轮速、加速度稳定度和持续静止时间判断静止状态；
- 标定完成前禁止角速度闭环，或明确使用 BNO085 自带标定值并移除重复零偏估计。

### IMU-P2-03：低质量或异常姿态也会直接参与转向控制

位置：

- `Application/Services/IMU/Src/imu_service.c`
- `Application/Services/Ctrl/Src/motion_service.c`，`heading_correct()`

当前四元数模长平方只要不小于 0.5，就会设置 `yawValid=true`。运动控制没有进一步检查：

- BNO085 accuracy/status；
- 是否仍处于零偏标定；
- 数据年龄；
- 四元数是否存在 NaN/Inf；
- 四元数模长是否异常偏大。

建议增加统一的 IMU 健康状态或快照接口，让控制器只消费满足质量要求的数据。

### IMU-P2-04：航向遥测累计旋转约 9 圈后溢出

位置：

- `Application/Tasks/ImuTask/Src/imu_task.c`，`send_heading_frame()`

内部 `yawDeg` 是连续不回绕角，但协议使用：

```c
int16_t yaw_ddeg = (int16_t)lroundf(yawDeg * 10.0f);
```

`int16_t` 最大只能表达 3276.7°，约 9.1 圈。超过范围后遥测会溢出；角速度字段也没有显式限幅。

建议：

- 若上层只需要朝向，发送前回绕到 `[-180°, 180°]`；或
- 协议升级为 `int32` 连续角；
- 转换前检查有限值并限幅。这里先由 `lroundf()` 得到 `long`，再窄化为 `int16_t`；超出 `int16_t` 范围的结果依实现而定，不应把普通的约 9 圈溢出直接描述成浮点转整数的未定义行为。NaN/Inf 或超出 `long` 范围需要另外处理。

### IMU-P2-05：IMU 数据存在跨任务非一致读取

位置：

- `ImuTask` 写入 `ImuService`；
- `MotionTask` 和遥测路径直接读取同一个结构体。

当前没有互斥、版本号或快照机制。对齐的单个 float 在 Cortex-M7 上通常不会撕裂，但一次控制计算仍可能组合出不同采样时刻的 yaw、yawRate、status 和 lastUpdateMs。

建议提供只读快照接口，使用短临界区、互斥锁或 sequence counter，保证一组字段来自同一版本。

### IMU-P2-06：GOAL 模式尚未接入 IMU 航向闭环

位置：

- `Application/Services/Ctrl/Src/motion_service.c`，`handle_goal()`

`handle_goal()` 直接使用 `motion_goal_step()` 的舵角结果，没有调用 `heading_correct()`。因此当前 IMU 只影响：

- `MOTION_DRIVE`；
- `MOTION_DIRECT_CONTROL`。

不会修正 GOAL 的直线或圆弧轨迹。设计文档也将 GOAL 接入标记为待完成，因此该项属于已知功能缺口。

### IMU-P2-07：控制器符号说明与实际实现不一致

位置：

- `Application/Services/Ctrl/Inc/heading_control.h`
- `docs/IMU-Heading-Control-Design.md`
- `Application/Services/Ctrl/Src/heading_control.c`

头文件和设计文档使用 `psiRef - yaw` 的传统误差定义，而实现根据当前“正曲率表示右转”的约定使用 `yaw - psiRef`。前进方向的当前实现是有意设计，但文档不一致容易导致后续 Agent 在调参或重构时错误翻转符号。

建议在代码、公式和测试中统一以下约定：

- yaw 正方向；
- 曲率正方向；
- 前进/倒车时 `yawRate = f(v, kappa)` 的关系；
- 控制误差和输出方向。

## 4. 完整控制链路与安全问题

### CTRL-01 / P1：航向修正越界后转向回到名义中位（已复现）

证据位置：

- `heading_control.c:165–175`：只限制修正量 ±0.30，直接返回 `kappaFf + corr`；
- `steering_lut.c:104–115`：超出 `STEERING_KAPPA_MAX_1PM=3.770` 返回 false；
- `motion_service.c:914–920、969–976`：映射失败时令 `raw_steer=0`，DRIVE 还令等效舵角为 0。

输入 `kappaFf=3.770`、前进速度 0.2 m/s、实测角速度为 0，现有控制器输出 4.070，LUT 返回失败。调用方随后使用名义中位，而非保持最大允许转向。DRIVE 的轮速计算也会退回直行。

这是满舵、起步和转向尚未跟上时容易满足的条件。因实际直行中位已有 -30 µs 补偿，`raw=0` 对应的 1500 µs 也不等于当前标定的 1470 µs。

修复方向：先对最终可执行曲率统一限幅，再用同一曲率计算舵机和双轮速度；积分抗饱和应跟踪最终执行器限幅。数值异常和映射失败应产生明确诊断/受控降级，不应静默变成直行。

### CTRL-02 / P1：STOP/故障停车可被旧运动快照覆盖（代码确定，调度待复现）

证据位置：`motion_service.c:584–597、617–640、736–740、EmergencyStop()、LatchFault()`。

可行交错：

1. MotionTask 在锁内复制 DRIVE 目标，然后释放 `targetMutex`；
2. MotionTask 在获取舵机/电机互斥锁或其他可阻塞点让出运行；
3. CtrlTask 或 SafetySupervisor 设置 ESTOP/故障并硬停电机；
4. MotionTask 恢复，继续使用旧的 `current_target`，调用 `setTargetRPM()`，把驱动重新切回 CLOSED_LOOP。

下一轮 ESTOP 的 `handle_emergency_stop()` 主要维护舵机和软件目标，并不每周期重施电机硬停。因此风险不仅是一个周期的短脉冲，旧电机目标可能在上层已经显示 ESTOP 时继续保持。

优先修复方向：确立单一执行器写入者；STOP/故障使用不可被旧代次提交覆盖的锁存与命令代次校验。最终提交必须与停车请求串行化。简单在下发前再读一次 mode 仍存在检查与写入之间的竞争。

### CTRL-03 / P1：电机停止/制动失败未被可靠传播和重试（代码确定）

证据位置：

- `motor_service.c:221–225`：紧急停止获取电机锁超时会直接返回；
- `motor_service.c:247–269`：`brakeAll()` 某轮加锁失败后跳过，但函数最终仍返回成功；
- `motion_service.c:837–842、692–700`：忽略停止返回值；安全逻辑无条件置 `safetyBraked=true`。

如果某轮没有真正制动，上层仍认为已进入制动状态，后续又因 `safetyBraked` 跳过目标下发，缺少重试和失败升级。监督任务调用的停车路径也依赖这些任务锁，并非独立硬件输出通道。

修复方向：双轮结果分别报告，失败不得宣布“已制动”；控制层重复确认停止状态，独立 inhibit 保障失败时 PWM 不能恢复。STBY/使能脚是否能接入硬件关断需结合接线再设计，不能假定当前已有该功能。

### CTRL-04 / P1：动态航向目标导致舵机反复从零速起步（已复现）

证据位置：`servo_service.c:95–115、289–313`，`system_init.c:211–217`。

仅当目标变化不超过 0.001° 时保留轨迹。超过该阈值就重建 `smoothCtrl` 并将速度归零。IMU 反馈曲率持续变化，远非重复不变的离散目标。

按当前加速度 180°/s²、20 ms 舵机周期，每次从零起步的位移约为：

```text
180 × 0.02 × 0.02 = 0.072° / 次
```

临时测试每 20 ms 在 140° 和 140.01° 目标之间交替，从 90° 开始，2 秒后仅到 97.2°，速度仍只有 3.6°/s。若 MotionTask 每 5 ms 持续刷新变化目标，舵机任务可能持续无法建立正常速度。

修复方向：更新目标时保留速度状态，使用支持在线重规划的限速/限加速度器；需要改变方向时平滑减速。测试应覆盖不断变化的目标，不能只测试完全相同目标的刷新。

### CTRL-05 / P1：立即回中被死区提前返回，旧轨迹继续生效（已复现）

证据位置：`servo_service.c:184–203`。

`setAngleImmediate()` 先判断新角度与当前 commandedAngle 的差是否小于死区，满足时直接返回，未取消旧的 MOVING 轨迹。

复现：从 90° 启动向 140° 的平滑运动，执行一次 update 后当前位置 90.072°；此时请求立即回到 90°。因为差值小于当前 2° 死区，函数返回，但平滑目标仍是 140°、状态仍是 MOVING。

ESTOP 中反复回中可能后续才中断旧轨迹；GOAL 完成时只请求一次回中、之后 inactive 分支不再控制舵机，旧轨迹可能继续向外走。

修复方向：立即命令必须先取消旧轨迹并更新目标，死区只决定是否需要写 PWM。`setAngleSmoothly()` 的同类提前返回也需要检查，避免“请求取消运动但被忽略”。

### CTRL-06 / P1：超声波无时间戳且未纳入任务监督（代码确定）

证据位置：`SafetyChannel` 结构、`sonar_task.c:63–75、119–128`、`safety_supervisor.c:required`。

安全通道保存最后的距离/scale，没有最后一次成功更新的时间。SonarTask 不在 required heartbeat 集合中。一旦测距任务停止推进，旧的“安全距离”可以无限期放行，普通的 `everValid` 故障判定无法发现，因为只有调用 update 时才更新 fault。

另外，已在配置中启用的前后传感器，上电后若从未成功测到距离，会被当作未安装而完全放行。这是 fail-open 策略，和编译期明确禁用传感器应区别对待。

修复方向：安全通道带时间戳与 ready/stale/fault 状态；已启用的通道在启动宽限期后仍无有效数据时降级/禁止运动；将 SonarTask 纳入适当的健康监督。

### CTRL-07 / P1：障碍近场检测有中值滤波迟滞，固定距离未约束速度（已复现 + 待测风险）

证据位置：`safety_service.c:channel_median()/safety_channel_update()`、`sonar_task.c:59–90`、`ultrasonic_config.h`。

每路约 10 Hz，五点中值。旧窗口全为 100 cm 时，连续输入两个 5 cm 样本，输出仍为 100 cm，直到第三个近场样本才触发 blocked，临时测试已复现。

障碍出现到近场输出约需 0.2–0.35 s（依采样相位与取结果时刻），尚未包含机械制动。按配置的 1 m/s 名义上限，检测期本身对应约 20–35 cm 行程。当前 12 cm stop/40 cm slow 是固定值，不能由代码证明在所有速度、负载下足够。

修复方向：正常显示保留中值；紧急近场使用独立快速通道，并评估单次误测抑制；根据实测制动减速度建立 `停止距离 >= 延迟行程 + 制动距离 + 余量` 的动态速度上限。实际刹车距离必须落地测量。

### CTRL-08 / P2：两轮分别限幅改变实际曲率（已复现）

证据位置：`motion_kinematics.c:72–73、89–90`。

两轮各自 clamp 到 maxRPM，而不是同比缩放。临时输入 v=1 m/s、转角 28.5°、轴距 141 mm、轮距 167 mm、轮半径 32.5 mm，得到 300/199.349 RPM。由轮速反算曲率约 2.414 1/m，目标几何曲率约 3.851 1/m。

该例直接调用运动学函数；应用层 DRIVE 的曲率上限是 3.770，GOAL 的转角上限是 28.5°，两条路径边界略有差异。该饱和机制在高速度转弯时同样存在。

影响：舵机按照一种曲率，双轮速度差按照另一种曲率；落地后可能发生轮胎侧滑、控制环互相补偿，实际轨迹取决于机械约束。

修复方向：计算完整双轮目标后按最大绝对轮速同比缩放，优先保留曲率、降低整体速度；将单轮 trim 纳入最终可执行边界。

### CTRL-09 / P2：DIFFERENTIAL 模式不符合当前阿克曼机械约束（代码确定 + 待测风险）

证据位置：`motion_service.c:934–956`，`goal_cfg_from()` 的 `allowPivot=false`。

GOAL 已禁止原地旋转，但 DIFFERENTIAL 仍支持正负轮速原地差速转向，且把前轮舵机设为名义 90°。对当前有前轮连杆转向的底盘，这属于依赖轮胎滑移的动作，不能作为理想差速机器人执行任意 v/omega。

需要明确它是台架诊断模式还是正式移动模式。正式模式建议将 v/omega 转换为可行曲率、限制低速大角速度并拒绝不可行 pivot；若保留诊断能力，应明确门控。该模式的居中也应复用标定后的直行中位。

### CTRL-10 / P2：低速和直弯切换未清除角速度积分（代码确定）

证据位置：`heading_control.c:111–162`。

低速或倒车时虽然把 kappaMeas 设置成 kappaFf，使当前误差为零，但输出仍包含旧的 `rateIntegral`。因此“反馈不工作”不等于“修正为零”。直行分支也不清除 rateIntegral，转弯→直行→反向转弯可能重新带入上一个弯的积分。

修复方向：定义各子模式的进入/退出动作；低于反馈可用速度时冻结或衰减积分并明确是否输出零修正；换向/反向弯避免携带旧积分。

### CTRL-11 / P2：执行器读取失败伪装成真实零状态（代码确定）

证据位置：`motor_service.c:343–365`，`motion_service.c:1109–1187`。

读取电机状态加锁失败会返回全零结构，而运动层把它当成有效测量。若之前累计轮程非零，当前全零会产生一次大的反向里程增量，下次读取成功又产生相反跳变；GOAL 和堵转判断可能在中间错误完成/中止。

修复方向：返回显式成功标志、样本序号和时间戳；读取失败保留最后有效值，并使估计器/监督器知道样本过期，不能把错误编码成“真的停稳/轮程归零”。

### CTRL-12 / P2：共享运动/GOAL 状态的锁保护不完整（代码确定）

证据位置：`motion_service.c` 的 Set*、StartGoal、GetStatus 与 Run、handle_goal、update_runtime_state。

命令任务在 targetMutex 下写目标和 GOAL，但运动任务的大部分 GOAL 步进、完成判定、累计更新及 state 写入并未持有同一把锁。读取方加锁无法保护未加锁的写入。STOP/GOAL 切换时存在旧事务继续更新新事务状态的窗口。

修复方向：所有命令以消息/邮箱提交，由 MotionTask 独占运动事务；状态发布采用快照。若继续共享内存，应明确每个字段的唯一写入者与一致性范围，避免用长时间大锁覆盖全部控制链路。

### CTRL-13 / P2：标定接口和多个居中出口不一致（代码确定）

证据位置：`steering_lut.c` 的 `angle_to_pulse()` 与 `curvature_to_pulse()`；`motion_service.c:827–835、955–956、1028`。

曲率接口会应用 -30 µs 偏移，angle_to_pulse() 直接查原表，不带偏移。ESTOP 使用标定直行角；DIFFERENTIAL、GOAL 完成及映射失败则使用名义中位。零曲率、名义舵机角、真实前轮直行三个概念混用。

另：当前 141 mm 轴距下，28.5° 对应约 3.851 1/m，大于全局 3.770 上限。GOAL 可能允许生成 28.5°，随后 curvature_to_raw() 又拒绝，进一步触发回中。几何准入、规划限幅和执行器限幅应来自同一份参数。

修复方向：集中定义唯一的“物理曲率→安全脉宽”生产接口，诊断原表接口明确命名；所有回中出口使用标定零曲率；运行期配置校验确保角度、曲率与最小半径一致。

## 5. 硬件与控制系统风险

### HW-01：舵机命令角不是实测轮角（架构事实）

当前 commandedAngle 仅表示软件输出 PWM 的估计位置，系统没有前轮角度反馈。回差、齿轮打滑、供电下降导致的跟随误差不能靠状态字段识别。IMU 可以改善车辆运动时的航向，但不能证明静止时前轮实际达到某角度。

建议将字段和接口语义明确为 commanded/estimated；若后续需要真实角度闭环，增加舵轴/转向机构反馈。现阶段使用低速实车轨迹标定、记录进入方向、限制机械端点，避免用单一静态 LUT 承诺高精度轮角。

### HW-02：倾斜安装下 gyro.z 不等于世界竖直轴偏航角速度（待实测确认）

当前 yaw 来自四元数，yawRate 却直接取传感器坐标系 gyro.z，没有安装旋转变换或俯仰/横滚补偿。模块明显倾斜安装或车身上下坡时，两者不一定对应同一旋转轴。即使 yaw 解算仍能读出航向，也不能据此认定 gyro.z 的幅值完全正确。

建议记录传感器到车体的固定安装矩阵，对 gyro 三轴变换；若控制目标是世界 yaw 的变化率，再使用相应姿态运动学。先通过已知轴手转、不同倾角和左右圆弧核对符号与比例，不把安装方向假设直接当成已验证结论。

### HW-03：零偏跟踪会吸收真实慢转，且不会修正四元数 yaw（代码确定）

`imu_service.c:161–166` 仅凭角速度接近当前 bias 就慢速跟踪，不检查车辆是否静止。持续小于约 0.5°/s 的真实慢转会逐渐被吸收。同时该 bias 只作用于 yawRate，不作用于 SH-2 四元数 yaw，角度环和角速度环使用的估计可能逐渐不一致。

建议优先信任 SH-2 校准输出，若保留二次标定，必须定义静止检测、样本时间和重新标定策略。Game Rotation Vector 未提供磁北绝对参考，直行锁定适合短时相对航向，不应承诺无限期无漂移的绝对朝向。

### HW-04：舵机响应与轮速差立即生效，时间上不协调（待测风险）

DRIVE 用目标曲率立即计算左右轮速差，但舵机通过 90°/s、180°/s² 平滑规划慢慢到达。转弯刚开始时可能是“车轮尚未转到，后轮已执行对应差速”，外环随后继续放大反馈修正。

建议保留一个可执行曲率轨迹，以该轨迹同步生成双轮目标；降低航向外环频率并按实际传感器更新推进。不能把 PWM 软件轨迹当成机械已到位，仍需实测舵机延迟。

### HW-05：轮速同步、IMU、trim 与前馈缺少统一分工（优化建议）

当前 DRIVE 中 IMU 修正同时改变舵角与左右轮目标；之后 wheel_sync 又在轮速差≤3 RPM 时修改目标；右轮还有 1.023 speedTrimScale 和独立前馈。小曲率补偿可能被同步环重新拉回接近同速，产生抖动或长期积分。

建议先区分参数标定误差和执行器摩擦误差：轮径/编码器比例应进入测量标定，摩擦通过前馈和内环补偿；外环决定曲率，内环跟随各自目标。同步环若保留，应只在明确直行条件下工作并验证其与航向环的带宽分离。

### HW-06：电源、机械及 H 桥状态不能只凭软件证明（验收缺口）

本轮未测量舵机电源压降、STM32/ESP32 复位原因、制动电流、接地噪声和机械端点力矩。代码中的 brake 状态只是软件意图，需结合实际驱动真值表与接线，用示波器/电流测量验证 PWM、IN1/IN2、使能脚在急停、换向、复位时的状态。

当前接线文档将 STBY 固定到 3.3V，意味着软件监督不能通过它独立切断桥驱动。若安全目标要求 MCU/任务失效后也能迅速禁止驱动，可考虑外部使能链路；这是硬件增强建议，不能替代先修复 CTRL-02/03。

## 7. 统一修复优先级

按风险与依赖顺序分批处理：

1. **安全提交与执行器**：CTRL-02 STOP 竞争、CTRL-03 制动失败传播、CTRL-05 立即命令取消轨迹、CTRL-06 安全数据超时。
2. **基本控制正确性**：CTRL-01 最终曲率限幅、CTRL-04 动态目标跟随；IMU-P1-01/02 倒车符号、P1-03 直行判断。
3. **IMU 生命周期**：IMU-P1-04/05/06 数据新鲜度、初始化恢复、制动冻结；IMU-P2-01 恢复重捕获；CTRL-10 子模式积分管理。
4. **几何与数据一致性**：CTRL-08 同比限速、CTRL-11 测量失败标志、CTRL-12 单写者/快照、CTRL-13 标定和范围统一；验证 HW-02 安装轴变换。
5. **落地安全边界**：CTRL-07 检测延迟与速度上限、CTRL-09 模式机械约束、HW-04 舵机/轮速协调、HW-05 多环分工。
6. **功能完善与性能**：遥测范围、诊断降频、GOAL 接入 IMU、状态可观测性、长期漂移和标定管理。

每批修复都应补针对性回归。完成安全和基本控制批次前，不建议直接以最高速度进行落地调参。这里只给出修复与测试建议，本轮未实施修复。

## 8. 未提交改动评价

### 8.1 模式变化时重置参考航向

该思路可以避免从停止切换到运动时沿用上次参考航向，但实现仍有以下缺口：

- 只能识别 `MotionMode` 变化；
- 同一模式下的新控制事务不会触发；
- IMU 断线后恢复不会触发；
- 安全制动解除不会触发；
- 函数内部静态变量 `s_prevMode` 脱离 `MotionContext`，不利于重初始化和单元测试。

建议后续把航向控制器生命周期绑定到明确的运动事务、IMU 健康状态和安全制动状态，而不只依赖模式枚举变化。

### 8.2 每秒一次航向诊断日志

新增日志本身没有发现明显逻辑错误，但系统目前还包含：

- IMU 任务 10 Hz 的长文本日志；
- 10 Hz 航向遥测；
- 10 Hz 六轴遥测；
- 运动状态、超声波、ACK 等 UART 数据。

后续应在真实运行态测量 UART 占用、日志丢弃和 ACK 延迟，避免重新引入历史上出现过的上行拥塞问题。

| 动态平滑目标 | 140/140.01交替，20ms一次，共2s | 90→97.2，速度3.6°/s | 重规划反复清零速度 |

额外核查：直行→转弯→直行时，直行分支自身会清除角度积分，因此没有把这一点列为缺陷；真正遗留的是 rateIntegral 在低速和子模式切换时的生命周期（CTRL-10）。

Debug 构建和现有11组 host 测试已通过。针对相同产品代码基线进行的针对性复现用于说明现有测试未覆盖的逻辑，不把这些错误输出描述为“验收通过”。STOP竞争、任务挂起、硬件电源/制动距离和实际轨迹仍需后续受控测试确认。

### 12.3 结构决定

- `heading_correct()` 在 IMU 无效、数据过期、或安全制动时统一 `Disable()` 并回退开环；
  `Disable()` 同时清除参考角，恢复后自动重新捕获，避免带旧基准恢复。
- 最终曲率限幅放在控制器出口，保证 `steering_lut_curvature_to_raw()` 不会因越界失败。
